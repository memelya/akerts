GEN UI: надёжность модели и диагностика — 2026.11.02.10

ПРОБЛЕМА
Успешный тест с mock CLI подтверждает код интеграции, но не совместимость
с установленной GigaCode, выбранной в ней моделью и её реальным выводом.
До получения отчёта с вашего ноутбука работа реальной модели не подтверждена.
Ответ процесса с кодом 0 не означает, что график создан или применён.

ЧТО ИЗМЕНЕНО
0. Все модельные сценарии используют единый транспорт CLI: одинаковый разбор
   JSON, обработку запуска, тайм-аутов и диагностику выхода процесса.
1. В режиме GigaCode обычный точный запрос больше не проходит через сценарий
   поиска аномалий: модель выбирает параметры графика, сервер считает CSV,
   проверенный renderer рисует график. HTML/JS от модели для этого не нужен.
2. Исследования остаются отдельным модельным сценарием: отбор -> локальные
   факты -> модельный анализ со ссылками -> проверка -> готовые компоненты.
3. Генерация совершенно нового HTML/CSS/JS остаётся экспериментом с явной
   опцией. Проверка структуры не доказывает, что код отрисуется в браузере.
4. Ошибки фоновых задач содержат место остановки, границу ответственности,
   подтверждённую причину или указание, что причина неизвестна, следующий шаг,
   необходимость менять запрос и идентификатор запроса.
5. Короткая диагностика реальной CLI запускается на вашем ноутбуке. Она
   не читает CSV и не передаёт модели продукты, ID и наблюдения пользователя.

КАК ПРОВЕРИТЬ
В распакованной новой версии откройте консоль и выполните:
  python diagnose_project.py
Это только проверка конфигурации и сводка последних 200 записей лога.
Затем:
  python diagnose_project.py --probe-model
Будет до трёх настоящих вызовов настроенной CLI; они могут расходовать квоту.
Не запускайте одновременно запрос в браузере. Последовательно проверяются:
  A. Может ли CLI вернуть короткий JSON?
  B. Может ли она вернуть допустимые параметры обычного графика?
  C. Может ли она вернуть минимальный код компонента под контракт сайта?
После первого провала дальнейшие тесты не выполняются. Каждый вызов ограничен
настроенным временем. Нельзя обещать успех всех последующих задач по этим тестам.
Проверка C валидирует серверный контракт, а не исполнение кода в браузере.
Диагностика не меняет конфигурацию CLI, CSV, справочники и сохранённые графики.
Вызовы записываются в обычный локальный лог с префиксом diagnostic-.

Передайте файл diagnostics-report.json из корня проекта.
В нём нет исходных CSV, запросов, ответов модели, аргументов запуска,
полных путей, имён продуктов и токенов из конфигурации. Есть ОС, Python,
версия проекта, настройки бюджетов, статусы и продолжительность тестов.
Идентичность модели пока отмечается not_confirmed: CLI может выбирать её
из своего окружения. Укажите выбранную модель отдельно, если знаете.
Если нужен подробный разбор, локальный gigacode-log.json содержит исходные
ответы и запросы, а при ненулевом выходе процесса — stderr (до 8 КБ).
Этот подробный лог нельзя считать обезличенным; проверьте его перед передачей.

ПРИЧИНЫ И ДЕЙСТВИЯ
* CLI не найдена / не настроена: исправляется установка или ai-config.json.
  Переформулировка вопроса и добавление CSV здесь не помогут.
* Тайм-аут: известно только, что процесс не успел. Это не доказательство
  отсутствия авторизации. Сначала короткий тест A; затем B и C.
* JSON не получен: проверить ответ CLI, оболочку responsePath и формат вывода.
  Пояснение вокруг одного полного JSON допустимо. Повреждённые/несколько
  объектов не угадываются. Контракт кода и фактов остаётся строгим.
* Ошибка полей/пояснений/ссылок: несовместимость модельного ответа с платформой.
  Не следует заставлять пользователя искать магические слова в вопросе.
* Лимит данных: ограничение сервера, не «слабый запрос». Рейтинг считается
  по всей выбранной выгрузке в SQLite; исследование не поддерживает любое
  число строк без ограничения. Разбивать исследование следует явно.
* Нет наблюдений: проверьте период и канал; справочник описывает опросы,
  но не заменяет дневные строки наблюдений.
* Один ID в двух каналах: укажите канал. Самовольно смешивать их нельзя.

ЧТО ДАТЬ НА ВХОД
Обычный график: показатель + опрос/продукт + период + группировка + канал,
если один номер есть в обоих источниках. Например:
  Покажи отправки по опросу 514 пуш+смс по дням за октябрь 2026 года.
  Покажи ответы по опросу 3434 экран успеха по месяцам за 2026 год.
Отправки, ответы, CSI и отсечения считаются из реальных CSV, не моделью.
Для дневного графика нужны day_part и дневные строки выбранного периода.
Для продукта нужна его связь с номерами в date/products.csv.
Для отклонений от плана нужен план: справочник либо явная цель в запросе.
Для выяснения причин нужен журнал запусков/изменений или другой источник
контекста. По одним объёмам можно найти отклонение, но нельзя доказать сбой.

ПОРЯДОК ПРИЁМКИ НА РЕАЛЬНОЙ GIGACODE
1. Пройти тесты A и B на вашем ноутбуке; зафиксировать модель и версию CLI.
2. В браузере отключить «Создать новую визуализацию», выбрать GigaCode CLI.
   Построить один простой месячный и один дневной график по существующему ID.
   В логе должен быть настоящий вызов, числа должны совпасть с CSV.
3. Проверить уточнение другого канала и добавление ровно одной кривой.
4. Проверить рейтинг и исследование отдельно, сверить состав расчёта.
5. Только после теста C включить новую визуализацию: увидеть предпросмотр,
   проверить значения, применить. Сохранение без отрисовки успехом не считать.
6. Повторить фиксированный набор реальных вопросов несколько раз; считать
   долю доведённых до видимого результата запросов, задержки и сбои по этапам.

ДАЛЬНЕЙШАЯ АРХИТЕКТУРА
Обычный рабочий путь — смысловой план модели и проверенный UI платформы.
Свободная генерация кода не должна быть зависимостью каждого графика.
Следующий шаг после реального отчёта — компактный версионированный контракт
выбора данных и декларативной композиции UI, с понятными допустимыми действиями.
Свободный код остаётся отдельной экспериментальной веткой. Увеличение тайм-аута
и числа повторов не заменяет исправление первого несовместимого этапа.
